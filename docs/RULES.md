# 检视规则与口径（RULES）

本文件固化看板的判定口径，任何一次定时任务都应遵循；口径变更请直接改这里。

## 1. 服务对象

- 账号：`zzzzwwjj`
- 上游仓库：`vllm-project/vllm-ascend`
- 责任田：以仓库 `.github/CODEOWNERS` 为准（`@zzzzwwjj` 出现的规则）

## 2. 什么进入检视范围

采集只有一条查询：`is:pr is:open review-requested:zzzzwwjj updated:>=上次运行`。

之所以够用，是因为：

- 分支保护强制 code owner 检视 → 改了我负责的文件时 GitHub 会自动把我加进 reviewer；
- 这次 push 会刷新 `updated_at`，落在窗口内；
- 人工“请求我 review”也会刷新 `updated_at`（已实测：25 个样本中 6 个“请求晚于最后一次提交”，其 `updated_at` 均不早于请求时间）。

## 3. 去重规则（严格）

**只要 PR 在 `state.prs` 里出现过，就永不再进入新一期**，无论是否精读、head 是否变化。

- 被过滤的数量记在 `stats.skipped_seen`（页头“历史已见”）；
- 草稿、我自己的 PR、我已给结论的 PR 记在 `stats.skipped_other`（“其他过滤”）；
- 草稿不写入 `state.prs`，转正式后仍算新 PR，会重新出现。
- **例外**：通过 issue 显式请求的 PR（页面「需要检视 / 刷新检视」）会绕过去重，本期强制重审。

## 4. 精读规则与配额

- **issue 请求的 PR 全部优先精读**（可超过 20 条）；
- 请求数 < 20 时，用本期新增 PR 补足到 20 条；剩余新增进“未精读列表”；
- 例：请求 15 + 新增 10 → 精读 15 个请求 + 5 个新增，另 5 个新增只列表；
- 请求 25 → 25 个全部精读，新增全部只列表；
- 没有请求时每期精读数 = min(20, 本期新增数)，不足 20 不补历史；
- **只评审责任田内的文件**：一个 PR 哪怕改了上百文件，也只针对 `owned` 里那部分下结论；
  需要上下文时只跳读相关函数/调用方，不评审、不评价非责任田文件；
- 精读必须基于 head 真实代码核对，不得臆造；把握不足时 `confidence=low` 并写明要作者确认什么；
- 结论三档：`approve`（可批准）/ `look`（需细看）/ `pushback`（建议打回）；
- 风险分 `high / medium / low`，只写具体风险，不写套话。

### 4.1 两种检视模式

| 模式 | 触发条件 | 做法 |
|---|---|---|
| **深度精读**（`mode: deep`） | PR 含 `@zzzzwwjj` 责任田内的文件 | 只针对 `owned` 文件逐项分析，见第 4 节 |
| **简单检视**（`mode: light`） | PR **不含**责任田文件，但被显式请求（reviewer 指定 / 页面「需要检视」「刷新检视」） | 只看 PR 描述、CI、以及明显问题（冲突、CI 红、超大 diff、缺测试、明显接口破坏），不逐文件深挖；结论注明“由对应 code owner 深入检视” |

- `mode` 写在精读 JSON 里，缺省按 `deep` 处理；
- 页面在无责任田文件的卡片上显示“简单检视”标记；老数据即使没写 `mode`，只要 `owned` 为空也按简单检视展示。

## 5. 历史积压期

首期（`2026-11-23-0015`）是历史积压，不是某一轮增量：

- 范围：尚未合入、待我检视、且不在近四期、也不是上次运行之后新增的 PR；
- 只列不精读，`backlog: true`、`label: "历史积压"`；
- 构建脚本：`collect-backlog.mjs` + `build-backlog-edition.mjs`（一次性）。

## 6. CODEOWNERS 变更

- 每期重新拉取，无缓存；拉取失败或解析为 0 条规则时终止本期；
- 不做哈希对比、不做变更提示、不回溯历史期次；
- 缩小责任田：历史只会多覆盖，不会漏；扩大责任田：相关 PR 在下次 push/请求时被带出。

## 7. 回复、批注与规则学习

- 每张精读卡片可提交回复，落成 `[feedback]` issue；
- 按提交人区分：`@zzzzwwjj` 的回复视为批注（蒸馏规则）；其他人的回复视为讨论（回应并视情况刷新精读）；
- 每期收录后：写回 `state/feedback.json`（含回应/采纳结论），并把批注蒸馏 1–3 条规则进 `state/lessons.json`；
- 规则要泛化、≤80 字、总量 ≤15 条；精读时最多注入 10 条与改动路径相关的规则。

## 8. 高优检视

高优检视是**一个批次视图**（`?hl=1`），不是逐条列表；左侧栏只有一个入口，样式与期次卡片一致
（名称 / 待处理数 / 绿蓝红三色点）。

条目来源：

- `[remind] PR #n`：只加入高优，不刷新、不换批次；
- `[refresh] PR #n`：重新精读后从原批次移到最新一期，并加入高优；
- 页面“需要检视”按钮等同于 `[refresh]`；
- **作者也可以请求**：首页搜索不到自己的 PR 时，可直接点「需要检视」，下一期精读并进入高优。

**移出条件（两选一）**：

1. 已标记“完成检视”（`data/db/marks.json` 有该 PR）；
2. 我在 GitHub 上已在该 PR 当前 head 给过结论（approved / changes requested / commented）。

服务端发布 `highlights.json` 时会按上述条件过滤，侧栏数字因此是精确的。

## 9. 完成检视（marks）

- 页面「完成检视」按钮默认**直接提交仓库**：浏览器 `PUT data/db/marks.json`（需要 Contents 写权限的 token）；
- 提交后页面轮询到站点更新（约 30–60 秒）即变成“已检视”；失败自动退回 issue 方式；
- 每次发布前 `render.mjs` 会先从远端合并 marks，避免本地状态覆盖网页上的标记；
- issue 方式（无 token 或权限不足）会在下一期被 `[done]` 收录后生效。

## 10. 数据不可变

已发布的期次内容不回溯修改（除一次性的积压替换与去重重算）。补丁类修正只作用于最新一期。
